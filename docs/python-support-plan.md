# Python Support Implementation Plan

Implementation status (2026-07-10): phases 0–7 are implemented on the
`python-support` branch, including a Gitea 1.26.2 end-to-end run. The architectural
decisions below are normative; operator instructions live in `workflows.md`, `cli.md`,
and `bundle-format.md`.

Companion to [ADR 0005](decisions/0005-python-package-transfer-without-python.md).
This plan describes the target design, configuration and bundle format changes, the
module map, and the implementation phases.

## Goal

Extend the existing download/publish workflow so that Python dependencies of
configured Git targets (and explicit pypi targets) are collected into the bundle on
the online side and published into Gitea's PyPI registry on the offline side, without
requiring Python or pip on either machine running `airgap-sync`.

Consumer outcome in the closed network:

```bash
pip install --index-url http://gitea.local/api/packages/pypi/pypi/simple/ <package>
```

or the equivalent `pip.conf` / `PIP_INDEX_URL` configuration generated by the publish
phase.

## Data Flow

```text
online
  requirements*.txt / uv.lock / pylock.toml from Git mirrors + explicit pypi targets
    -> traverse requirements roots with their pins and hashes as constraints
    -> consume exact lock graphs or simplified closure for unlocked specs
    -> select wheel files per configured target environment
    -> download + sha256 verification
    -> python-packages/ + python-seed-manifest.json

closed network
  python-seed-manifest.json
    -> multipart POST each file to {giteaUrl}/api/packages/{owner}/pypi
    -> 409 Conflict accepted only after target sha256 verification
    -> python-publish-report.json
    -> generate pip index configuration for consumers
```

Python collection participates in the existing fixed-point loop: newly mirrored Git
repositories are scanned for Python manifests in the same iteration that scans
`package.json` files.

## Configuration

`airgap-sync.json` additions (absence of `pythonTargetEnvironments` disables Python
collection entirely, keeping existing workspaces unaffected):

```json
{
  "pythonSourceIndex": "https://pypi.org/simple/",
  "pythonTargetEnvironments": [
    {
      "name": "prod-linux",
      "pythonVersion": "3.11.9",
      "os": "linux",
      "arch": "x86_64",
      "manylinux": "manylinux_2_17"
    }
  ],
  "pythonPublishOwner": "pypi"
}
```

- `name` labels the environment in reports and manifests.
- `pythonVersion` is the full interpreter version so patch-sensitive
  `python_full_version` markers are deterministic.
- The acceptable wheel tag list (interpreter, ABI, platform, including older
  `manylinux` levels and `abi3`/`none-any` fallbacks) is derived internally, in pip's
  preference order. A raw `platformTags` array is an escape hatch for exotic targets.
- Marker evaluation (`python_version`, `sys_platform`, `platform_machine`, ...) uses
  the same environment entries.
- Linux targets explicitly select `manylinux`, `musllinux`, or raw `platformTags`.
  Optional marker overrides provide values such as `platform_release` only when a
  dependency needs them.
- The publish endpoint is derived from the existing `giteaUrl` plus
  `pythonPublishOwner`; authentication uses the current Gitea login and saved token.

Target specs:

```bash
airgap-sync target add pypi numpy==1.26.4 --python-resolution-mode approximate
airgap-sync target add pypi "requests[socks]>=2.31" --python-resolution-mode approximate
```

## Bundle Format Additions

```text
airgap-bundle/
  python-packages/
    numpy-1.26.4-cp311-cp311-manylinux_2_17_x86_64.manylinux2014_x86_64.whl
  python-seed-manifest.json
  python-metadata-cache.json
```

`python-seed-manifest.json` records everything publish needs so that the offline
phase never parses wheel archives:

```json
{
  "schemaVersion": 1,
  "createdAt": "2026-07-06T00:00:00.000Z",
  "sourceIndex": "https://pypi.org/simple/",
  "targetEnvironments": [{ "name": "prod-linux", "pythonVersion": "3.11.9" }],
  "packages": [
    {
      "name": "numpy",
      "version": "1.26.4",
      "requiresPython": ">=3.9",
      "files": [
        {
          "file": "python-packages/numpy-1.26.4-cp311-...whl",
          "filename": "numpy-1.26.4-cp311-...whl",
          "kind": "wheel",
          "pythonTag": "cp311",
          "sha256": "...",
          "url": "https://files.pythonhosted.org/...",
          "environments": ["prod-linux"],
          "metadataVersion": "2.1"
        }
      ],
      "resolvedFrom": [
        { "type": "locked", "raw": "numpy==1.26.4", "requiredBy": "acme/app uv.lock" }
      ]
    }
  ]
}
```

Reports: the collect/fetch reports gain a `python` section (resolved, downloaded,
skipped, unsupported, missing-wheel errors); publish writes
`python-publish-report.json` next to `publish-report.json`; the run history under
`runs/` includes both. `prune` learns a `python-package` object type.

## Module Map

New subsystem under `src/core/python/`:

| Module                | Responsibility                                                         |
| --------------------- | ---------------------------------------------------------------------- |
| `names.ts`            | PEP 503 name normalization                                             |
| `pep440.ts`           | Version/specifier operations (thin wrapper over `@renovatebot/pep440`) |
| `requirements.ts`     | PEP 508 requirement parsing: name, extras, specifier, marker           |
| `markers.ts`          | Environment marker evaluation against a target environment             |
| `wheels.ts`           | Wheel filename parsing, tag expansion, compatibility ranking           |
| `environments.ts`     | Config entry -> ordered acceptable tag list                            |
| `index-client.ts`     | PEP 691 JSON index + PEP 658/714 metadata fetch                        |
| `metadata.ts`         | Core-metadata (RFC 822) parsing; `python-metadata-cache.json`          |
| `requirements-txt.ts` | `requirements*.txt` parsing                                            |
| `uv-lock.ts`          | `uv.lock` parsing                                                      |
| `pylock.ts`           | Standardized `pylock.toml` parsing                                     |
| `resolver.ts`         | Locked path + simplified closure                                       |
| `fetch.ts`            | Download, verification, manifest writing                               |
| `publisher.ts`        | Gitea PyPI upload                                                      |
| `verify.ts`           | Static bundle checks + optional pip-based install verification         |

Touched existing modules: `types.ts`, `workspace.ts` (config + pypi targets),
`collect.ts` (fixed point), `git-manifests.ts` (generalize file extraction from bare
mirrors to Python manifests), `apply.ts`, `prune.ts`, `verify.ts`,
`verify-install.ts`, `cli.ts`, the menu, and docs.

New dependencies: `@renovatebot/pep440` (PEP 440), `smol-toml` (uv.lock is TOML; the
repo currently has no TOML parser).

## Phases

Each phase lands with its tests and keeps `npm run check` green.

### Phase 0 — Spikes

- Validate `@renovatebot/pep440` coverage: epochs, pre/post/dev releases, local
  versions, `~=`, `===`, prerelease-exclusion defaults. Fallback if gaps are found:
  port the (well-specified) version/specifier logic from `packaging`.
- Confirm the TOML parser choice against real `uv.lock` files.
- Record outcomes in this document.

**Outcome (2026-07-06): both libraries adopted.**

- `@renovatebot/pep440` 5.0.0 passed the full spike matrix, including the PEP 440
  ordering traps it defines deliberately: `>1.0` rejects `1.0.post1`, `<1.0` rejects
  `1.0.dev1`, epochs order before release segments, `==1.0` accepts `1.0+local`,
  wildcard `==1.4.*`, and `===` arbitrary string equality. `maxSatisfying`/`filter`
  implement the `packaging` prerelease rule (pre-releases only when nothing final
  satisfies), which matches pip and is what `resolver.ts` needs.
- `smol-toml` 1.7.0 parsed a real-world 365-package `uv.lock` (pydantic-ai) in ~50 ms.
  Confirmed structure: `package[]` with `name`, `version`, `source`
  (`registry`/`editable`/`git`/`virtual`), `wheels[]` (`url`, `hash`, `size`),
  `sdist`, `dependencies[]` (name plus optional `marker`), `optional-dependencies`,
  and top-level `requires-python`/`resolution-markers`. Note for Phase 3: sdist-only
  packages occur in real locks and must hit the wheels-only reporting path.

### Phase 1 — Pure machinery (no I/O)

- `names.ts`, `requirements.ts`, `markers.ts`, `wheels.ts`, `environments.ts`.
- Exhaustive unit tests, including a fixture corpus of real wheel filenames
  (numpy, torch, cryptography, pydantic-core) and marker expressions.
- Marker comparison follows the typed field rules current as of January 2026. Full
  Python patch versions and explicit Linux compatibility levels avoid guessed target
  properties.

### Phase 2 — Index client and metadata cache

- PEP 691 client with API-major validation, relative URL handling, and
  `Accept: application/vnd.pypi.simple.v1+json`; a clear error for indexes that only
  serve HTML.
- PEP 658/714 `core-metadata` download, legacy alias support, and hash verification.
  Fallback when a file has no metadata
  entry: download the wheel itself and read `METADATA` from the zip archive (the
  wheel is usually needed anyway; dry runs use temporary storage only).
- `python-metadata-cache.json` keyed by source index plus artifact URL/hash; retries
  and timeouts through the existing `retry.ts`/`fetcher.ts` conventions.

### Phase 3 — Inputs

- `requirements-txt.ts`: requirements and constraints with extras/markers/`--hash`,
  line continuations, comments, `-r` includes, and `-c` constraints. Editable installs,
  URL/path/git lines, and
  index options are reported as unsupported with `requiredBy`, mirroring the npm
  unsupported-spec policy.
- `uv-lock.ts`: exact versions, dependency edges, and per-file URLs + hashes (lock
  URLs can be used directly for download).
- `pylock.ts`: lock version 1.0, environments, package markers, dependency groups,
  exact versions, wheels, URLs, and hashes.
- `target add pypi <spec>` in workspace/CLI/menu.
- Python input discovery (`requirements*.txt`, `uv.lock`, `pylock*.toml`) in configured
  Git mirrors and Git dependency mirrors. Development files/groups use `includeDev`.
  A `pyproject.toml` without a supported lock is reported with remediation guidance.

### Phase 4 — Collection

- Resolve unlocked requirements independently per target environment, aggregate
  constraints deterministically, and union the resulting package versions/files.
- Locked path: select the lock graph for each environment and download exact files.
  When a requirement carries
  `--hash` values, the chosen wheel must be among them or the package is reported.
- Simplified closure for requirements and direct targets per ADR 0005: highest
  satisfying version,
  `Requires-Dist` recursion, marker evaluation as the union across target
  environments, extras support, cycle handling, `requiredBy` edges.
- Per-environment wheel selection with `requires-python` checks; yanked files are
  skipped unless pinned exactly (pip behavior).
- Bundle writing (`python-packages/`, `python-seed-manifest.json`), integration into
  the `collect.ts` fixed point, prune support, report sections.

### Phase 5 — Publish

- `publisher.ts`: standards-compatible multipart upload built entirely from the seed
  manifest, HTTP Basic login/token auth, dry-run mode, verified-idempotent 409 handling,
  and actionable package-size errors.
- Orchestration in `apply.ts`, `python-publish-report.json`, run history.

### Phase 6 — Verification and operator UX

- Static verify checks: file/hash/manifest consistency, per-environment coverage
  warnings (package present but no file for environment X).
- Optional install verification: when a suitable Python interpreter exists on the
  verifying machine, create a venv and `pip install` the workspace's pinned
  requirements against the Gitea index; otherwise record a skipped-with-reason entry.
- Consumer configuration generation (`pip.conf` snippet / `PIP_INDEX_URL`) in the
  apply report, analogous to Git `insteadOf` rules.
- Menu integration; docs updates: `cli.md`, `bundle-format.md`, `architecture.md`,
  `README.md`.

### Phase 7 — End-to-end

- Extend `e2e:local` to publish into Gitea's PyPI registry and, when `python3` is
  available on the dev machine, verify with a real `pip install`.
- Offline integration test: a small closure (for example `requests`) resolved from
  committed PEP 691/PEP 658 fixtures served over a local HTTP server in vitest.

## Testing Strategy

- Committed fixtures of real PyPI JSON index and `.metadata` responses under
  `test/fixtures/python/`.
- Wheel selection matrix tests: given real file lists, assert the chosen file per
  target environment.
- Requirements corpus tests covering supported pins and every unsupported line type.
- Publisher tests against a stub HTTP server (upload fields, auth, 409, size-limit
  errors); e2e against real Gitea.

## Risks and Fallbacks

- `@renovatebot/pep440` gaps → Phase 0 spike; fallback is porting `packaging` logic.
- Missing PEP 658 metadata on old releases → wheel-download fallback in Phase 2.
- Unpinned closure under-collection (pip backtracking) → documented lock-first
  recommendation, approximate-result marking in reports, install verification.
- Gitea specifics (per-owner scoping, size limits, name normalization) → covered by
  e2e; deployment requirements documented in ADR 0005.
- Bundle size growth from multi-platform wheel sets → per-environment size totals in
  the fetch report so operators see the cost of each configured environment.

## Out of Scope for v1

- `poetry.lock`, `Pipfile.lock`, `pdm.lock` (parser slots exist behind the same
  internal model).
- All sdist collection and any closed-network build story.
- Resolving unlocked `pyproject.toml` project metadata.
- Private source-index authentication.
- Python Git/URL/path requirements mirroring (future work can reuse the existing Git
  mirror machinery and `insteadOf` configuration).
- Multiple source indexes / `--extra-index-url`.
- Propagating yank state into the closed-network registry.
